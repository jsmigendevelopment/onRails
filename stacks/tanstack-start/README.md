# TanStack Start starter

A small, working app to start from: TanStack Start (React, TypeScript strict) on Cloudflare Workers, with D1 through Drizzle, Clerk for sign-in, shadcn/ui and Tailwind CSS, TanStack Query, Zod, Vitest and Playwright.

It runs, tests and builds with no accounts and no keys. Without Clerk keys, sign-in is off and every notes call is refused.

It starts secure, fast, accessible and search-ready: security headers and a nonce CSP on every response, rate and body limits on server functions, budgets and Lighthouse checks, axe on every route in both themes, and the SEO files built for you. See [On by default](#on-by-default).

## What's inside

```
src/
  routes/            thin file routes: load data, render a module's view
    api/v1/          the versioned HTTP API (server routes) for mobile and desktop clients
  modules/
    home/            the landing page
    notes/           the example module: list (search, order and pages in the URL), a note's own
                     page, create, rename, delete, owned by the signed-in user
      ui/views/      notes-view.tsx, note-view.tsx (loading, empty, error, stale and signed-out states)
      ui/sections/   recent-notes-section.tsx (streamed behind Suspense)
      ui/components/ note-create-form.tsx and note-rename-form.tsx (TanStack Form, loaded lazily
                     by lazy-note-forms.tsx), note-item.tsx,
                     notes-filter.tsx, note-not-found.tsx
      hooks/         notes-queries.ts (keys and query options, for loaders), use-notes.ts (list and
                     optimistic writes), notes-cache.ts (the optimistic cache changes)
      server/        notes.functions.ts   server functions: method, auth, one controller call
                     notes.http.ts        /api/v1/notes: Request in, Response out, same controller
                     notes.controller.ts  parse input, call the service, return the envelope
                     notes.service.ts     business rules. No HTTP, no SQL
                     notes.repository.ts  the port the service depends on
                     notes.repository.drizzle.ts / .memory.ts  D1 adapter and test fake
                     notes.table.ts       the Drizzle table
      schemas.ts     Zod schemas shared by the form and the server
      search.ts      the route's search and params parsers (plain functions: they ship with every page)
      types.ts
  components/ui/     shadcn/ui primitives
  components/        shared app components (header, theme toggle, empty, error and 404 states, page
                     skeleton, refresh status, error toast)
  hooks/ lib/ db/    shared hooks, helpers (error type, logger, paging, SEO, headers, env schema), the D1 client
  server/            request-guards.ts (headers, CSP, limits), auth.ts (Clerk, actor), env.ts,
                     turnstile.ts, composition.ts (the one place that wires adapters)
public/              _headers, icons, share image, web manifest
scripts/             generate/ (the new:* generators and their templates), budgets/ (bundle budgets),
                     migrations/ (the migration lint), pr/ (pull request rules), check-licenses.ts,
                     check-merge.ts (+ checks/), deploy.ts (+ deploy/), test-visual.ts,
                     generate-icons.ts, setup-cloudflare.mjs (+ cloudflare/)
```

The rules: a module never imports another module, shared code never imports a module, and a service never imports the database, HTTP or an SDK. `pnpm lint` fails if any of that happens (`eslint.config.js`). The owner's code style is enforced the same way: see [Code rules](#code-rules).

**Always use a generator** to create a module, route, section, component or table. Each one writes the right shape, wires it in, and passes `pnpm check` as it is:

| Command                                                   | Makes                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm new:module <name> [--item <singular>] [--no-route]` | `src/modules/<name>/`: `ui/views`, `ui/sections` (Suspense > error boundary > content, a skeleton of the same shape, ErrorState), `ui/components`, `hooks`, `server` (functions, controller, service, repository port, Drizzle adapter, memory fake, table), `schemas.ts`, `types.ts`, `copy.ts`, tests for each layer; its factory in `composition.ts`, its migration, and the page at `/<name>` |
| `pnpm new:route <path> <module>`                          | `src/routes/<path>.tsx` and, if missing, the module's `<last-part>-view.tsx`; the route tree; the path in `e2e/helpers.ts` (axe and screenshots)                                                                                                                                                                                                                                                  |
| `pnpm new:section <module> <name>`                        | `ui/sections/<name>-section.tsx` from the module's list query, and its test                                                                                                                                                                                                                                                                                                                       |
| `pnpm new:component <module> <name>`                      | `ui/components/<name>.tsx` (presentational) and its test                                                                                                                                                                                                                                                                                                                                          |
| `pnpm new:table <module> <name>`                          | `server/<name>.table.ts` with `id`, `created_at`, `updated_at` (snake_case, epoch-ms UTC), and its migration                                                                                                                                                                                                                                                                                      |

Names are kebab-case; a module name is plural (`todo-items`). A new page needs its screenshots: `pnpm test:visual --update --docker`.

Add `--dry` to any generator, before or after its words (`pnpm new:module tasks --dry`), to see the plan first: it prints the files it would create, the files it would edit and the tools it would run (ESLint, Prettier, drizzle-kit), and writes nothing. It refuses for the same reasons the real run does.

## Set up Clerk

1. Create an application at clerk.com (the free tier is enough).
2. Copy `.env.example` to `.env` and fill in `VITE_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` (or let `clerk env pull` write them: those are the names Clerk's CLI uses). Never commit `.env`. The old name `CLERK_PUBLISHABLE_KEY` still works, with a warning.
3. `pnpm dev`, open `/notes`, sign in.

The server reads the keys per request in `src/server/auth.ts`. The signed-in user comes from the verified Clerk session, never from the request body. The CSP opens Clerk's Frontend API host (read from the publishable key) only when the keys are set.

A session token is accepted only from the app's own origins (Clerk's `authorizedParties`, `src/lib/authorized-parties.ts`): `SITE_URL`, localhost in a local build, and the test Worker's workers.dev URL and `pr-<n>` previews in a test build. Add any other origin to `CLERK_AUTHORIZED_PARTIES` (exact origins, comma-separated). Production with Clerk keys needs `SITE_URL` or `CLERK_AUTHORIZED_PARTIES`, or the Worker refuses to start.

## Turnstile (optional)

Add it only when counters show the cheaper layers are not enough. Create a widget in the Cloudflare dashboard, set `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`, and the note form starts sending a token; `withHumanCheck` verifies it. The script loads on the form's first focus, never on page load.

## Environments

| Where      | Worker           | D1 database      | Deployed by                                           |
| ---------- | ---------------- | ---------------- | ----------------------------------------------------- |
| local      | (none)           | `app`, local     | `pnpm dev`, tests                                     |
| test       | `app-test`       | `app-test`       | `pnpm deploy:test` from main, after each merge        |
| previews   | `app-test` alias | `app-test`       | `pnpm deploy:preview <n>`, before review              |
| production | `app-production` | `app-production` | `pnpm deploy:production`, only after the person's yes |

Each environment has its own block under `env` in `wrangler.jsonc`. Bindings are not inherited: an add-on that adds a binding adds it to the top level and to both environments. The build picks the environment (`CLOUDFLARE_ENV=test pnpm build`); `wrangler deploy` then uses the build's flattened config. D1 commands take `-c wrangler.jsonc` so they read the source config, for example `pnpm exec wrangler d1 migrations apply DB --remote -c wrangler.jsonc --env test`.

Rename `app`, `app-test` and `app-production` (Worker and database names) in `wrangler.jsonc` before the first setup. Locally, `pnpm db:migrate:local` applies the migrations to the local D1. To change the schema: edit the module's `*.table.ts`, run `pnpm db:generate`, read the SQL, commit it. Never edit a migration that has already run.

## Set up Cloudflare

An agent runs this for the person, dry run first:

```sh
node scripts/setup-cloudflare.mjs --dry-run   # reads only: what exists, what it would create or change
node scripts/setup-cloudflare.mjs             # below Full, after the person says yes; on Full, without asking
```

It checks `wrangler whoami` (if not signed in, the person runs `pnpm exec wrangler login`), creates the test and production D1 databases if missing and writes their ids into `wrangler.jsonc`, creates any R2 bucket or queue an add-on declared, deploys the test Worker once if it doesn't exist yet (`pnpm deploy:test`'s commands, as the Coming soon page, so pull request previews have something to upload to; `--no-first-deploy` skips it; never production), and runs the kit's `push-secrets.mjs --wrangler` for the app's secrets. With a custom domain (a production `routes` entry, or `--zone example.com`) and a separate zone token in `.env.cloudflare.local`, it applies the free zone settings: Always Use HTTPS, minimum TLS 1.2, AI training crawlers disallowed (never blocked: that would also stop Google and Bing), and a WAF rule that blocks scanner paths. Bot Fight Mode is recommended once the custom domain exists and is the person's choice (`--bot-fight-mode`): the CSP allows its same-origin `/cdn-cgi/` script on the production domain, and the production smoke test runs on workers.dev, outside the zone. Cloudflare's managed robots.txt stays off (`--managed-robots`): it duplicates the app's own. What it makes for the smoke tests goes to `.env.cloudflare.local` (git-ignored, mode 600), never printed. With `ci = "local"` in `docs/stack.md` it writes nothing to GitHub; only with `ci = "actions"` does it also set `CLOUDFLARE_ACCOUNT_ID` and those values in the GitHub environments and explain the Actions deploy token. Run it again any time; it skips what exists.

It also asks how to protect the test and preview URLs, and records the answer as `SITE_PROTECTION` in `env.test.vars`:

```sh
node scripts/setup-cloudflare.mjs --protect access --logins google --allow-emails you@example.com  # recommended
node scripts/setup-cloudflare.mjs --protect access --allow-domain company.com                      # PIN only, a whole domain
node scripts/setup-cloudflare.mjs --protect access --logins github --allow-github-org acme
node scripts/setup-cloudflare.mjs --protect password                                               # a password page in the app
node scripts/setup-cloudflare.mjs --protect none
```

Access puts a Cloudflare sign-in in front of the whole test Worker and its previews, static files included, and creates a service token for the smoke tests. setup-cloudflare saves it in `.env.cloudflare.local` as `TEST_CF_ACCESS_CLIENT_ID` and `TEST_CF_ACCESS_CLIENT_SECRET`, where the deploys read it, and never prints the secret. A token made before that, whose secret isn't in the file: refresh it in Zero Trust → Service credentials and put both values there. It needs Zero Trust on the account and an account token in `CLOUDFLARE_ACCESS_TOKEN` (`.env.cloudflare.local`).

- **Logins** (`--logins`, comma-separated): `google` (recommended), `github`, `facebook`, `linkedin`, `yandex`, `entra` (Microsoft work accounts), `oidc` (any other OpenID Connect provider). A one-time PIN by email is always on as the fallback. Discord is not offered: Access has no Discord login, and Discord does not document an email in its ID token.
- **Each login needs an OAuth client the person makes.** The first run prints their "Setup step for you" with the exact callback URL, then stops. The client id and secret go in `.env.cloudflare.local` (`ACCESS_GOOGLE_CLIENT_ID`, `ACCESS_GOOGLE_CLIENT_SECRET`, and so on), never on the command line, never printed.
- **Who may sign in:** `--allow-emails a@x.com,b@y.com`, `--allow-domain company.com`, `--allow-github-org <org>` (with the GitHub login). Any match lets them in. Emails are never written to a file.

**Production too, after the person's yes.** `--protect-production all` puts Access in front of all of production (the internal-tool default); `--protect-production /admin/*,/ops/*` only those paths, on workers.dev and the custom domain. Same logins and people. Production is on the always-stop list: dry run first, show the person, and the real run needs `--production-ok`. The production smoke test sends its own service token, which setup-cloudflare saves as `PRODUCTION_CF_ACCESS_CLIENT_ID` and `PRODUCTION_CF_ACCESS_CLIENT_SECRET` in `.env.cloudflare.local`.

**The Worker checks Access's token too.** Wherever `SITE_PROTECTION` is "access", every request on a protected path (`ACCESS_PATHS`, default all, minus `OPEN_PATHS`) must carry a valid `Cf-Access-Jwt-Assertion`: signed by the team's key, for this app's AUD, not expired. Anything else gets the 401 envelope. setup-cloudflare writes `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` and, for production paths, `ACCESS_PATHS` into that environment's vars. `src/lib/access-jwt.ts`, with `jose`.

The password option makes a random `SITE_PASSWORD`, saves it in `.env.cloudflare.local` as `TEST_SITE_PASSWORD`, then sets it on the test Worker, never printed: the deploys send it as `x-site-password`, and the person reads it in that file. Neither a token nor a password is made when that file can't be written, and a new token whose secret couldn't be saved is deleted again. If `wrangler secret put` fails, the setup stops with exit 1 and says to run it again with `--protect password --new-password`, since the file now holds a password the Worker may not have. Paths that must stay open (a signed webhook) go in `src/lib/open-paths.ts`.

The app's secrets per environment: `pnpm connect` in your own terminal walks each provider, asks for each value with hidden input and stores it in `.env.local` and `wrangler secret put`, plus `gh secret set` only with `ci = "actions"` (stdin only, a yes per destination, production asked separately). `pnpm connect clerk` does one provider; `pnpm connect --dry-run` shows what's set, by name. Or by hand: `pnpm exec wrangler secret put CLERK_SECRET_KEY --env test`.

## Deploys

Every deploy runs from the agent's session (or your terminal), never from GitHub Actions. Sign in to Cloudflare once with `pnpm exec wrangler login` (or set `CLOUDFLARE_API_TOKEN` in the shell).

- **Test:** `pnpm deploy:test`, from a clean checkout of main after each merge. It builds, applies the migrations to the test D1, deploys, and runs `pnpm test:deployed` against the deployed URL. If anything fails after the deploy (no URL, a failed smoke test, a crash), `wrangler rollback` puts the previous version back, and it prints what to put in a bug issue.
- **Previews:** `pnpm deploy:preview <n>`, on the pull request's exact head commit with no uncommitted changes, before review. It uploads a version of the test Worker with the alias `pr-<n>`, checks it answers, and keeps one comment with its URL up to date. It uses the test database and never migrates it (the comment warns when the pull request adds a migration). Skipped for forks and the `lane:tiny` label.
- **Production:** `pnpm deploy:production --confirm "deploy production"`, only after the person's yes. Without the confirmation it prints the plan and changes nothing. It builds with `SITE_URL`, takes a D1 Time Travel bookmark, migrates, deploys and smoke-tests. A failed migration or deploy step prints the restore command with the bookmark; any failure after the deploy also rolls back the code. Restoring data is the person's call.

Test and production deploy only GitHub's main: each fetches it first and stops, deploying nothing, when the checkout is behind it or has a commit that isn't on it. All three run `pnpm install --frozen-lockfile` first. Test and production install the smoke test's browser before they write anything. If `wrangler deploy` itself fails, it reads `wrangler deployments list --json`: wrangler makes the new version live before it sets routes, domains and crons. Only when the newest deployment is new since the deploy started and carries this run's message is that version smoke-tested and rolled back like any other; otherwise nothing is rolled back (a rerun of the same commit carries the same message). A Worker's first deploy has no earlier version to roll back to, and the stop says so. If a rollback fails too, the stop message says the new version is live and untested, with the command to roll it back by hand. One deploy of each kind runs at a time (a lock file in git's common folder; a lock left by an ended run is taken over under a second file, so only one run gets it), and only with the pnpm `packageManager` pins. The deploy output is masked: secret-looking names, and the protection's values by value.

A protected site's smoke test needs its values in the shell or `.env.cloudflare.local` (git-ignored): `TEST_CF_ACCESS_CLIENT_ID` and `TEST_CF_ACCESS_CLIENT_SECRET`, or `TEST_SITE_PASSWORD`, for test and previews; `PRODUCTION_` ones for production. Without them, the deploy stops before it changes anything.

**Going live.** Production deploys with `LAUNCHED` "false" in `env.production.vars`, so every visitor sees "Coming soon" and the smoke test checks that page. Only the person decides to go live: then a pull request sets it to "true", and the next production deploy opens the app (the smoke test then checks the app).

A rollback restores code, never data, so a migration must work with the code before it: add columns and tables first, remove them in a later release. Set `SITE_URL` (in the shell or `.env.cloudflare.local`) before the first production deploy. `TEST_APP_URL`, when set, is the address the test smoke test uses, before the workers.dev URL. Set `PRODUCTION_APP_URL` only when there is no workers.dev URL to smoke-test: production prefers workers.dev, outside the zone. For your own domain, uncomment `routes` under `env.production` in `wrangler.jsonc`, and keep `workers_dev` on: the production smoke test runs there.

## HTTP API (`/api/v1`)

For clients that aren't this web app (mobile, desktop, scripts). The web app itself keeps using server functions.

| Method and path            | Body                                     | Success                                                                    |
| -------------------------- | ---------------------------------------- | -------------------------------------------------------------------------- |
| `GET /api/v1/notes`        | `?cursor=&limit=` (1 to 100, default 20) | `200 { ok: true, data: { items: NoteDto[], nextCursor: string \| null } }` |
| `POST /api/v1/notes`       | `{ title }`                              | `201 { ok: true, data: NoteDto }`                                          |
| `PATCH /api/v1/notes/:id`  | `{ title }`                              | `200 { ok: true, data: NoteDto }`                                          |
| `DELETE /api/v1/notes/:id` |                                          | `200 { ok: true, data: { id } }`                                           |

`NoteDto` is `{ id, title, createdAt, updatedAt }` (times in epoch milliseconds). Every request needs `Authorization: Bearer <Clerk session token>` (from `getToken()` on the client, fresh per request); the session cookie is never accepted here. A failure is `{ ok: false, error: { code, message, fields? } }` with the code's status: 400 `validation`, 401 `unauthenticated` (with `WWW-Authenticate: Bearer`), 404 `not_found` (also for another user's note), 405, 411, 413 `too_large`, 429 `rate_limited` (`Retry-After`), 500 `internal`. Bodies are JSON, at most 64 KiB, with no unknown fields. The schemas are `src/modules/notes/schemas.ts`. Optional `CLERK_JWT_KEY` (the instance's PEM public key) verifies tokens without a call to Clerk.

## Code rules

`guide/code-style.md` in the kit, turned into tools. A rule a tool can check fails the build; the reviewer judges the rest.

| files: warn at 300 lines, fail at 500; functions about 60 lines and complexity 15 (warnings)                                                       | `max-lines`, `max-lines-per-function`, `complexity`                                                                                |

| a route that is not fully server-rendered says why                                                                                                 | `local/ssr-needs-reason` (`eslint-rules.js`)                                                                                       |
| unused files, exports, dependencies                                                                                                                | knip (`knip.jsonc`)                                                                                                                |
| duplicated code                                                                                                                                    | jscpd (`.jscpd.json`)                                                                                                              |
| unsafe migrations                                                                                                                                  | `scripts/check-migrations.ts`                                                                                                      |
| security patterns                                                                                                                                  | Semgrep community rules for TypeScript and React (`pnpm check:merge`)                                                              |
| pull request tied to an issue, under 1,000 changed lines                                                                                           | `pnpm pr:rules <n>`                                                                                                                |
| the UI doesn't change by accident                                                                                                                  | `pnpm test:visual --docker` (`pnpm check:merge`)                                                                                   |

**An exception** is a decision someone can revisit: a comment with the reason and an issue number, on the line or the line above.

```ts
// eslint-disable-next-line no-console -- the build prints its own summary (#42)
// @ts-expect-error -- the SDK's type is wrong until v3 (#42)
```

A migration that must drop or rename (nothing to keep yet, and the person agreed) carries `-- migration-lint-allow dropped-column: <reason> (#42)`. Warnings (size, complexity) don't fail lint: split by responsibility when one shows up.

## Checks before merge

The pack ships no GitHub Actions workflows, and `docs/stack.md` says `ci = "local"`. Before a pull request merges, an agent other than its builder runs these on its exact head commit in its own clean clone, with no tokens and an empty home folder, and records the result as the `onrails/check` commit status (the kit's `coordinate` skill):

1. `pnpm check`, then `pnpm test:e2e` (`pnpm exec playwright install chromium` once).
2. `pnpm check:merge`: the pnpm `packageManager` pins, the bundle budgets, a check that migrations match the tables, `pnpm audit --audit-level=high`, the licence allow-list, no `.clerk/` files committed, `docs/research` (with the kit's checker), gitleaks (over a copy of the files git tracks at `HEAD`, so a dev checkout's git-ignored keys aren't scanned) and Semgrep (a local binary, else Docker), and the screenshot tests in Playwright's Linux image (Docker). A check this machine can't run is skipped with the reason; name every skip in the pull request.
3. The pull request rules, which the gate checks with the kit's `pr-rules.mjs` from its checkout of main (`feat/` and `fix/` branches only), never the pull request's own script. `pnpm pr:rules <n>` runs them by hand: `Closes #<n>` (or Fixes, Resolves) and a `feat|fix|chore/<n>-name` branch, unless it has the `no-issue` label (Dependabot is exempt), and under 1,000 changed lines (lockfiles, generated files and test fixtures not counted, with the kit's `pr-size.mjs`) unless it has the `size-exception` label and a `Size exception: <reason>` line in the description.

The agent-file guard (`agent-files.mjs`) runs from the session too. Never add a workflow: if a tool's docs say "add this workflow", run its commands from the session as a package script.

**Screenshots.** Baselines live in `e2e/visual.spec.ts-snapshots/`, one per page, theme and device. After an intended UI change: `pnpm test:visual --update --docker`, look at every changed PNG, commit them. Fonts render differently on macOS, Windows and other Linux images, so baselines made outside Playwright's image fail there. `--docker` mounts the git root and installs from there, so it also works from `apps/web` in the monorepo pack, where the lockfile is at the root. On a Linux host, the files the root container writes are handed back to the mounted folder's owner when it ends. Under rootless Docker or Podman they are already yours, so nothing is changed. No Docker? Skip them and say so in the pull request. `--docker` was written from a workflow the pack no longer has, and is not yet run by the kit's authors.

**Dependabot** opens one grouped npm update a week, and the security updates `setup-github.mjs` turns on. Nothing merges on its own: each bump is a normal pull request through the same checks and review. A pre-commit hook (lefthook) formats and lints the staged files. `pnpm install` installs it only when the folder is already a git repository: after `git init`, or in a git worktree, run `pnpm hooks` once. Without the hook, `pnpm check` and the merge gate still run every check.

Playwright is the browser test runner. A person's own browser (for example Claude in Chrome) is for a look after Playwright passes, never instead of it.
